Discussion topics on where to take the track mapper project.

Definitions:
Run8 server, r8server : An instance of the Run8 simulator running in server mode. In this mode, the simulator supports multiple users and keeps track of all of the trains and rail vehicles (RVs).
Rail Vehicle, RV, rvs : A rail vehicle represents a rail car, or locomotive within the Run8 simulation.
Train : A train represents a linked list of rvs.
Tag, Destination tag : A tag is a human readable moniker associated with either an rv or train. If on a train, the train tag is typically the "destination tag" (as named in the world save) of the lead locomotive.
World Save : An xml file which either captures the entire state of the world (if created on a r8server), or a subset of the entire world (near the player location) if created by a client. Big benefit to grabbing the entire world save is that we get the state of all RVs on the server. This file is routinely updated as a backup (and can be used to recreate the world state if the r8server crashes). Typically refreshed once every 2 minutes.
DispatcherComms.dll : a .net dll which can be used to access certain dispatcher functions on a remote r8server  

Goal #1: Host web server(s) which allows users to view the maps and location of trains as they exist on a particular r8server. We should be able to support multiple server instances - with the URL determining which r8server the user will monitor. 
Status: This appears to be working when running on a local machine - the maps are rendering, the world save is loaded routinely, and the trains are plotted. This has yet to be tested remotely. We currently have no solution as to how to regularly download world saves from a remote server.
To do: Investigate how to transfer world saves to the machine hosting the track mapper web server. Ideally this would be as lightweight as possible for the server operator. 

Goal #2 (possibly): Live tracking of trains via DispatcherComms.dll - giving a more real-time view of the status of moving trains.

--- DispatcherComms API review (2026-08-28) ---
Reviewed ExtDSAPIReference.pdf (Run8ExternalDispatcherWork/DispatcherSampleV2/Documentation).
Key finding that reframes this goal:

* NO train position. TrainData carries NO track-section index, NO distanceTravelled,
  NO lat/lon. Its only spatial field is BlockID = the signal block detector the LEAD
  loco occupies (-1 if none). That is BLOCK granularity, not the per-metre placement
  the world-save pipeline already gives. So DispatcherComms CANNOT move a train dot
  along a section - it is not a higher-fidelity replacement for world-save positioning,
  and cannot be interpolated into one.

* What it IS good for = a live CTC / dispatcher board feed (the thing a world save
  cannot show), refreshed continuously over TCP, per route:
    - Signal aspects (Signals: every DS-controlled signal's Stop/Proceed/Fleet/FlagBy)
    - Switch state (ReversedSwitches, UnlockedSwitches, OccupiedSwitches, InterlockErrorSwitches)
    - Block occupancy (OccupiedBlocks)
    - Live per-train metadata keyed by TrainID: TrainSpeedMph vs TrainSpeedLimitMPH,
      EngineerType (Player/AI/None) + EngineerName, TrainSymbol, HoldingForDispatcher, etc.
    - Sim time, IsClient flag, radio text / DTMF tones.
  => Complementary to the world save: world save = geometry & position (the spine);
     DispatcherComms = live signal/switch/block state + train telemetry overlaid on top.

Architecture implications:
  1. .NET event/push API -> needs a small C# sidecar holding the persistent IRun8
     connection; it exposes accumulated state to the Python server over local HTTP/ws.
     Note "V2 cycles routes one by one" -> keep PER-ROUTE state (each event is a full
     snapshot for one route), not one global dict.
  2. Requires dispatcher PERMISSION granted in-game (no permission -> zero data) AND a
     live TCP connection to the r8 instance's dispatcher port. This reintroduces the
     firewall/live-connection problem the world-save uploader (Goal #1) avoids, so it
     only works where the web host can reach the r8server. Keep it strictly OPTIONAL
     behind the existing /api/trains-style contract.
  3. Stay READ-ONLY: consume only "from Run8" events; never call ThrowSwitch/ChangeSignal/
     StopAITrain/etc. (IsClient + the doc's dueling-auto-dispatcher warning are why).
  4. Real work = ID reconciliation with our extracted geometry:
       - Signals arrive as a POSITIONAL array (indexed) -> need route -> signal-index ->
         our-signal mapping.
       - Switches by SwitchID, blocks by block-detector ID -> do we currently capture the
         dispatcher-facing SwitchID / block-detector ID in region_extractor? (gating item)
       - Trains by TrainID: OPEN QUESTION whether this equals the world-save train_id; if
         not, correlate via LocoNumber+RailroadInitials (or TrainSymbol <-> destination tag)
         to fuse live telemetry onto world-save-positioned trains.
  5. Convenient: DispatcherComms route IDs (100 Mojave, 110 Needles, 120 Cajon, ...) are
     exactly our config route_prefix values - route-keying already consistent, no translation.

Bottom line: still a "would be nice", priority unchanged, but the feature is NOT "smoother
trains" - it is "live signal/switch/block CTC overlay + live train telemetry" via an optional
C# sidecar, for operators who can give the host a dispatcher connection. Goal #1 (world save)
stays the universal baseline; this is a richer overlay where the connection exists.

--- Goal #1: remote world-save transport - design + plan (2026-08-28) ---
Decisions locked this session:
  * Host = ONE central MULTI-TENANT server on a DigitalOcean Linux droplet (paid, ours).
    URL path selects the server:  /s/<server_id>/...
  * Operator runs a SMALL AGENT WE PROVIDE (single-file Windows .exe, no Python install).
  * STANDARD published Run8 routes ONLY (host already has/gets the geometry).

Transport principle: PUSH, never pull.
  Remote r8servers sit behind home NAT; pull (SFTP/SMB/port-forward) = operator friction we
  reject. The agent pushes OUTBOUND over HTTPS (443 always open, no firewall changes). Even
  "on-demand" stays push-initiated (agent opens/holds an outbound channel; host asks over it).

KEY DEPLOYMENT INSIGHT (DO = Linux, NO Run8 install -> and it doesn't need one):
  Track GEOMETRY is generated ONCE on a Windows box that HAS Run8
  (output_generator.py -> output/<name>/ : index.html, manifest.json, data/<region>.json),
  then DEPLOYED static to DO. Because routes are standard, geometry is identical per route
  for every operator. The DO host does NOT parse .r8/.tr4 and does NOT need Run8 - it only
  needs the generated region JSON (+ db_railvehicles.db) to place trains from an uploaded
  world save. serve.py ALREADY reconstructs section polylines from region JSON with no
  track-DB reload, so live-placement machinery exists; multi-tenant is mostly per-server
  bookkeeping around it.  => Only the WORLD SAVE (train state) crosses the wire to DO.

Components to build:
  A. Uploader agent (Windows, operator side) - Python + PyInstaller -> one .exe.
     - Config (agent.ini next to exe): host_url, server_id, token, save_folder, poll_seconds.
     - Watch the FIXED file "Auto Save World.xml" (Run8 always mirrors the newest save to it;
       see Autosave layout below). No newest-of-glob / prune logic needed. Poll mtime.
     - It is OVERWRITTEN each cycle, so guard against torn mid-write reads: on mtime change,
       wait until SIZE is stable across 2 polls (full 2-min gap = plenty of slack) before
       hashing. Skip if content hash == last uploaded. (Host also validate-parses on ingest,
       so a torn upload is rejected + last-known-good kept - belt and suspenders.)
       Optional hardening if torn reads ever appear: watch newest TIMESTAMPED
       "Auto Save World <ts>.xml" instead (immutable once written).
     - gzip the XML (~10:1) -> POST https://host/s/<server_id>/world
       Authorization: Bearer <token>; retry w/ exponential backoff; auto-resume after outage.
     - v1.5: honor a {watchers:0} response by backing off (idle upload bandwidth -> ~0).
  B. Multi-tenant host (extends serve.py):
     - Registry: server_id -> {token hash, display name, region/output set, save slot}.
     - POST /s/<id>/world (bearer auth): size cap, gunzip, VALIDATE parses via world_parser,
       atomic temp+rename into that server's slot, keep last-known-good, version = now/mtime.
     - Generalize serve.py's single --world watch into a dict keyed by server_id; reuse
       build_section_placer / extract_trains from region JSON per server.
     - Per-server endpoints: /s/<id>/ (map), /s/<id>/api/trains, /s/<id>/api/ping.
       Each /api/trains browser poll updates last_seen[id] (drives watcher-gating in A).
  C. Public-internet hardening (serve.py is stdlib http.server - do NOT expose it raw):
     - Front with Caddy (auto Let's Encrypt TLS, simplest) or nginx; bind Python to 127.0.0.1.
     - Proxy enforces TLS + request size cap + rate limiting. ufw: only 80/443 open.
     - Run serve.py under systemd (restart on fail) + log rotation.
     - Tokens: long random, store only a HASH; per-server isolation (a token writes only its slot).

Viewer UX (staleness): /api/ping already reports world; surface save AGE in the viewer
  ("updated 40s ago" / "stale 6m") so users can tell live from frozen. Cheap, high trust value.

Build/deploy flow (per hosted route/region set):
  Windows(+Run8): output_generator.py <config> -> output/   =>   rsync/scp to DO   =>
  register server_id + issue token   =>   hand operator the agent .exe + a filled agent.ini.

Autosave layout (CONFIRMED 2026-08-28 via screenshot of a live SouthernCA server):
  Dir: ...\Run8 Train Simulator V3\Content\V3Routes\Regions\<REGION>\AutoSaves  (per-region!)
    - "Auto Save World <YYYY.MM.DD HH.MM.SS>.xml"  = journal, ~10 kept, rotated, IMMUTABLE.
    - "Auto Save World.xml"                        = fixed name, always mirrors NEWEST. <-- TARGET
    - Each xml has a paired 1 KB ".info" sidecar (ignore for v1; may hold cheap sim-time/region).
    - "Auto Save Train.*" is a DIFFERENT save (not the world) - ignore.
    - Cadence ~2 min; size ~1.6-1.8 MB xml (-> ~150-250 KB gzipped). Trivial 24/7.
    - Dir path encodes the REGION -> free check that operator's server_id matches baked geometry.

Open items to confirm (not blocking the design):
  * Full-world only: agent must point at the SERVER's full-world autosave dir (a CLIENT save
    is partial/near-player - avoid/reject). (The AutoSaves dir above is the server's full-world.)
  * Confirm serve.py has no Windows-only path assumptions before running on Linux.
  * Multi-tenant config shape: one master registry file vs a per-server config dir on DO.

Phasing:
  P1: single hard-coded server_id end-to-end (agent push -> DO slot -> trains plot remotely).
  P2: multi-tenant registry + tokens + per-server routing + hardening (Caddy/systemd/ufw).
  P3: watcher-gating (v1.5) -> optional reverse-channel on-demand (v2) + staleness badge.

--- serve.py robustness: benign client-disconnect + torn-read hardening (2026-08-30) ---
Symptom: noisy traceback on startup - "Exception occurred during processing of request ...
ConnectionAbortedError [WinError 10053]" during a GET /api/trains write. Cause: a client (a
superseded 3s poll / reload / closed tab) drops the connection mid-response; sendall raises.
Recovers (per-thread) but logs an ugly trace, PLUS a secondary bug: do_GET's except caught the
disconnect and called _error(), which tried to write AGAIN to the dead socket -> second exception.
Fixes:
  1. _send_json wraps its send in try/except _CLIENT_DISCONNECT (ConnectionAborted/Reset/BrokenPipe)
     -> swallows the write-side disconnect and stops the do_GET re-error cascade.
  2. New _QuietThreadingHTTPServer(ThreadingHTTPServer) overrides handle_error to swallow any
     ConnectionError (covers BOTH read-side recv 10054 and write-side send 10053) with no traceback;
     everything else logs normally. daemon_threads=True. main() uses it.
  3. trains_payload wraps parse_world_save in try/except -> on a torn/partial read (Run8 rewrites
     the live save ~every 2 min) it serves the LAST-GOOD payload and retries next poll (cache mtime
     left unchanged), instead of 500-ing the client. Verified: torn read -> last-good, recovers on
     next valid save.
Tested: 6 RST-aborted requests -> 0 tracebacks in the log, server keeps serving (ping/trains 200).
